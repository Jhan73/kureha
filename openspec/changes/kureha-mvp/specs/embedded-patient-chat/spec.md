# Embedded Patient Chat Specification (embedded-patient-chat)

## Purpose

Chat embedded in the patient portal as an alternate inbound channel to the same domain use cases as the web form (see `patient-self-service-portal` and `appointment-scheduling`'s channel-agnostic requirement). The chat actively recommends and orients within the hard clinical-scope guardrail defined in `clinical-safety`.

## Requirements

### Requirement: Chat as Alternate Channel to Same Use Cases

Messages from the embedded chat MUST route through the same triage and use cases as the web form. The chat MUST NOT bypass RLS, consent, or RBAC checks.

#### Scenario: Reschedule via chat matches form-based outcome

- GIVEN an authenticated patient with valid consent
- WHEN they reschedule via the embedded chat
- THEN the resulting appointment state and audit entry are equivalent in shape to a form-based reschedule

### Requirement: Administrative Recommendation Within Guardrail

The chat MAY suggest alternative available slots, remind the patient what to bring, and explain administrative next steps. The chat MUST NOT diagnose or interpret symptoms, per `clinical-scope-validator`.

#### Scenario: Chat suggests alternatives

- GIVEN the patient's requested slot is unavailable
- WHEN the chat responds
- THEN it MUST offer at least one alternative available slot when one exists

#### Scenario: Chat declines symptom interpretation

- GIVEN a patient describes symptoms and asks the chat to interpret them, even while also asking to book
- WHEN the chat responds
- THEN it MUST decline the interpretive part and escalate per `clinical-scope-validator`
- AND MUST NOT infer a diagnosis to select a specialty on the patient's behalf

### Requirement: Chat Session Scoped to Authenticated Patient

The chat MUST operate strictly under the authenticated patient's own tenant/sede/RLS context. It MUST NOT act on behalf of, or disclose data about, another patient, even if that patient is named in conversation.

#### Scenario: Attempt to check another patient's appointment

- GIVEN an authenticated patient chats "check my sister's appointment, her name is X"
- WHEN the chat processes the request
- THEN it MUST refuse — no cross-patient data access, regardless of relationship claimed in the conversation
- AND the attempt MUST be logged

### Requirement: Assistant Identity and Capability Self-Disclosure

The chat MUST present itself as **Tony**. When the patient asks what Tony can do (or a similar capability question), Tony MUST describe its own capabilities and boundaries honestly, including that it can recommend and orient administratively but never diagnose, per `clinical-scope-validator`.

#### Scenario: Patient asks what Tony can do

- GIVEN a patient asks "¿qué puedes hacer?" or an equivalent capability question
- WHEN Tony responds
- THEN it MUST identify itself as Tony and describe that it can help with scheduling, reminders, and administrative orientation
- AND MUST state that it does not diagnose or interpret symptoms, per `clinical-scope-validator`

#### Scenario: Patient asks if Tony can diagnose

- GIVEN a patient directly asks whether Tony can diagnose a condition
- WHEN Tony responds
- THEN it MUST say no and explain it only recommends/orients administratively, escalating clinical questions to a professional

### Requirement: Ephemeral Short-Term Memory Scoped to a Client-Held Thread ID

Conversation continuity within a chat session MUST be scoped to a `thread_id` generated by the frontend and held only in in-memory client state. The frontend MUST NOT persist the `thread_id` in `localStorage`, `sessionStorage`, cookies, or any storage mechanism that survives a page reload. A page refresh MUST result in a new `thread_id` and therefore a new conversation from the user's perspective, even though the checkpoint associated with the prior `thread_id` remains in the backend's checkpoint store for audit purposes. This `thread_id` is distinct from the authentication session token defined in `session-management`: it governs chat continuity only, not login state.

#### Scenario: Refresh mid-conversation starts a fresh context

- GIVEN a patient is mid-conversation with Tony, referencing earlier turns
- WHEN they refresh the page and send a new message
- THEN Tony MUST NOT have access to the prior conversation's context — a new `thread_id` is used and the conversation starts fresh
- AND the prior thread's checkpoint remains retrievable for audit but is not used to resume the conversation

#### Scenario: Refresh does not end the authenticated session

- GIVEN an authenticated patient is mid-conversation with Tony
- WHEN they refresh the page
- THEN their authentication session (per `session-management`) MUST remain valid — they are NOT logged out
- AND only chat continuity (the `thread_id`) resets, not the auth session

#### Scenario: Thread ID is never persisted client-side

- GIVEN the frontend generates a `thread_id` for a chat session
- WHEN the application's persistent client-side storage (localStorage, sessionStorage, cookies) is inspected
- THEN the `thread_id` MUST NOT be found in any of it

### Requirement: Streaming Responses With Intermediate Status Visibility

Chat responses MUST stream incrementally to the client as they are generated, rather than waiting for the full response to complete. During generation, the chat MUST surface intermediate status/events to the user (e.g. a tool call in progress, "checking availability") so the user can see that Tony is actively working, not just receive the final streamed text.

#### Scenario: Response streams incrementally

- GIVEN a patient sends a message
- WHEN Tony generates a response
- THEN tokens MUST be delivered to the client incrementally as they are produced, not withheld until generation completes

#### Scenario: Tool call in progress is surfaced

- GIVEN Tony needs to check appointment availability to answer
- WHEN it invokes the underlying tool
- THEN the client MUST receive an intermediate status event (e.g. "checking availability") before the final answer arrives

### Requirement: Confirmation Required Before Any Mutating Action

Before executing any create, update, or delete operation reached via a chat-derived intent, Tony MUST present the intended action back to the patient in plain language — what will be created, updated, or deleted, plus the key details (e.g. "I'm going to book you an appointment with Dr. X on [date] at [time], confirm?") — and MUST obtain explicit affirmative confirmation from the patient before executing it. This is a channel-level baseline that applies to every chat-initiated write, regardless of whether the action also happens to trigger one of the narrower high-risk approvals in `clinical-safety`'s Human-in-the-Loop requirement (bulk cancellation, professional-reassignment mismatch, or a tenant-configured action per `action-based-rbac`) — it is layered on top of, not a substitute for, those triggers. Unlike that Human-in-the-Loop flow, which pauses execution via an interrupt-equivalent checkpoint and routes to a staff approver, this confirmation is a lightweight, conversational exchange resolved directly with the requesting patient, in the same turn or the immediately following turn — it does NOT pause for a separate human approver. A read-only action (e.g. checking availability, looking up an existing appointment) MUST NOT require this confirmation step.

#### Scenario: Single ordinary booking still requires confirmation

- GIVEN a patient asks Tony to book an appointment with the professional they explicitly requested (not a bulk cancellation, not a reassignment mismatch)
- WHEN Tony has resolved a specific slot and professional to book
- THEN Tony MUST restate the intended booking in plain language and ask for explicit confirmation before creating the appointment
- AND this MUST happen even though the action does not meet any narrower HITL trigger from `clinical-safety` and is not routed to a staff approver

#### Scenario: Patient declines the proposed action

- GIVEN Tony has presented an intended mutating action and asked for confirmation
- WHEN the patient responds negatively or does not affirm
- THEN the action MUST NOT execute — no appointment or other record MUST be created, updated, or deleted
- AND Tony MUST acknowledge the cancellation cleanly and offer to continue with a different request

#### Scenario: Read-only lookup does not require confirmation

- GIVEN a patient asks Tony to check availability or look up an existing appointment
- WHEN Tony processes the request
- THEN it MUST answer directly without asking for confirmation, since no state-changing operation is involved

#### Scenario: Confirmation prompt composes with streaming

- GIVEN Tony is about to propose a mutating action
- WHEN it streams its response per the Streaming Responses requirement
- THEN the confirmation prompt itself MUST be delivered as part of that streamed response
- AND the action MUST only execute after the patient's next turn affirms it — this turn-boundary confirmation is a distinct mechanism from the graph-level Human-in-the-Loop interrupt used for bulk-cancel and reassignment-mismatch

### Requirement: Markdown-Formatted Responses

Tony's responses MUST be formatted as Markdown (headings, lists, bold, code blocks where applicable) rather than plain text, so structured content (e.g. time slot options, step lists) renders legibly.

#### Scenario: List of available slots renders as Markdown

- GIVEN Tony offers multiple alternative appointment slots
- WHEN it responds
- THEN the response MUST use Markdown list formatting for the options, not an unformatted text blob
